# ADR 0001 — Technology & Dependency Versions

- **Status:** Accepted (pending engineer sign-off — see below)
- **Date:** 2026-08-17
- **Context:** Day 1, Step 2 (project scaffolding). We must pin a compatible, supported
  set of framework and library versions and record how each was verified. Per the
  engineer's instruction, versions are verified against **official / primary sources**
  (Maven Central artifact metadata and the official Spring Boot documentation), **not**
  endoflife.date and **not** model memory.

## Guiding principle

**Let the Spring Boot BOM govern every dependency it manages** (Flyway, PostgreSQL
driver, Testcontainers, Jackson, Spring Framework). We declare those dependencies
**without explicit versions** so the BOM guarantees a mutually-compatible set. We pin a
version **only** for artifacts the BOM does not manage — here, that is **springdoc
3.1.0** alone. This minimizes version-drift risk and is the most defensible choice.

## Primary sources (as consulted 2026-08-17)

1. **Spring Boot 4.1.0 system requirements** — `https://docs.spring.io/spring-boot/system-requirements.html`
   - Java 17–26; Maven 3.6.3+; Spring Framework 7.0.8+.
2. **Maven Central artifact metadata** (`maven-metadata.xml`, the authoritative record of released versions), retrieved directly from `repo1.maven.org`:
   - `org/springframework/boot/spring-boot-starter-parent` → release **4.1.0**
   - `org/springdoc/springdoc-openapi-starter-webmvc-ui` → release **3.1.0**
   - `org/flywaydb/flyway-core` and `flyway-database-postgresql` → latest standalone 13.3.0 (**not used**; BOM pins 12.4.0)
   - `org/postgresql/postgresql` → latest standalone 42.7.13 (**not used**; BOM pins 42.7.11)
   - `org/testcontainers/postgresql` / `testcontainers-bom` → 2.0.5 (matches BOM)
3. **Spring Boot 4.1.0 managed dependencies BOM** — `spring-boot-dependencies-4.1.0.pom` from `repo1.maven.org`, read directly for the managed `*.version` properties quoted above.

## Correction discovered during build validation (Testcontainers)

Initially we declared `org.testcontainers:postgresql` without a version, expecting the
Spring Boot parent to supply it. A `mvn compile` **failed**:
`'dependencies.dependency.version' for org.testcontainers:postgresql:jar is missing`.

Root cause: the Spring Boot 4.1.0 **parent** exposes a `testcontainers.version` property
and imports the `testcontainers-bom` **within `spring-boot-dependencies` for its own
managed artifacts**, but that import does **not** propagate Testcontainers module
version management into a downstream project. The documented, correct pattern is for the
project to **import `testcontainers-bom` itself**. We therefore added an explicit
`testcontainers-bom` import to our `dependencyManagement`, pinned to **2.0.5** (the exact
version the Spring Boot BOM uses), so no version drift is introduced. This is recorded
here rather than hidden because it is a genuine, defensible engineering decision found
through validation.

## Notable version facts to remember

- **Testcontainers 2.x renamed the module coordinates.** The PostgreSQL module is
  `org.testcontainers:testcontainers-postgresql` in 2.x (it was `org.testcontainers:postgresql`
  in 1.x). Using the old coordinates fails to resolve. Discovered during `mvn compile`
  validation and confirmed against Maven Central (`testcontainers-postgresql` release 2.0.5;
  the old `org/testcontainers/postgresql` path has no 2.x release). All 2.x modules carry
  the `testcontainers-` artifactId prefix.
- **Testcontainers 2.x** also changed some APIs versus 1.x (e.g. the Docker-Compose local
  path is now auto-detected rather than set via `withLocalCompose(boolean)`). We are on
  the 2.x line (2.0.5) via the BOM; test code must be written for 2.x APIs, not 1.x.
- **Jackson 3.x** (3.1.4) is the managed line under Spring Boot 4.1. The canonical
  serializer we build later must be validated against Jackson 3, not 2.x.
- Standalone-latest Flyway (13.x) and PG driver (42.7.13) exist but are **intentionally
  not** used, to stay within the BOM-verified set. Overriding would need its own ADR.

## Maven Wrapper (build reproducibility)

Maven was **not** installed on the development machine. Rather than depend on a global
Maven, we committed the standard **Maven Wrapper** so `./mvnw` / `mvnw.cmd` builds the
project with a known Maven version and no prior Maven install.

- **Generated with the official generator:** `maven-wrapper-plugin` (wrapperVersion
  **3.3.4**), invoked as `mvn wrapper:wrapper -Dmaven=3.9.9`. We did **not** hand-write the
  scripts or download them from an unverified source.
- **Pinned Maven version:** **3.9.9**, with the distribution URL pointing at the official
  `repo.maven.apache.org`. 3.9.9 satisfies Spring Boot 4.1's Maven 3.6.3+ requirement.
- **Distribution type:** `only-script` — the modern default. There is **no**
  `maven-wrapper.jar` to commit; only `mvnw`, `mvnw.cmd`, and
  `.mvn/wrapper/maven-wrapper.properties` are committed.
- **`.gitignore` correction:** the initial `.gitignore` (from Step 1) erroneously ignored
  `.mvn/wrapper/maven-wrapper.properties`. That line was removed — the wrapper properties
  file **must** be committed for the wrapper to pin its Maven version. This was caught with
  `git check-ignore`.

## Consequences

- `pom.xml` pins only `spring-boot-starter-parent` (4.1.0) and `springdoc` (3.1.0);
  all other dependencies inherit BOM-managed versions.
- The build is reproducible via the committed Maven Wrapper (Maven 3.9.9); contributors do
  not need a global Maven install.
- Re-verification: if we later bump Spring Boot, this ADR must be updated and the BOM
  re-read; springdoc compatibility must be re-checked against the new Boot line.
